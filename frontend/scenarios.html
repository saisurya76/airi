Usage scenarios by project type

Six concrete project types, each with the exact AIRI calls to wire in and what becomes measurable once you have — not hypothetical benchmarks, just the metrics each endpoint's own response already hands you. See What is AIRI? for what each piece does, and the Developers page for the full API reference every step below links back to.

1Customer support / AI helpdesk chatbot

Every inbound message goes to an LLM before a human sees it — one bad week (a viral thread, an outage spawning duplicate tickets) can spike the bill overnight if nothing checks size or cost per call first.

Integration steps

  1. Before generating a reply, send the message + conversation history to /analyze (or /analyze/exact once signed in, for real Claude/Gemini counts) with the model you'll actually use.
  2. If status comes back EXCEEDED, summarize or drop older turns rather than sending an oversized request and letting the provider reject it.
  3. Tag each real call's result with a label per queue (e.g. "billing", "technical") as it happens through the day.
  4. At shift end, POST the collected records to /report (or /report/pdf for a shareable summary) for a per-queue breakdown.

What to measure

  • Cost per conversation — total_cost / total_requests from /report, tracked per queue via by_label.
  • Overflow rate — status_counts.EXCEEDED / total_requests, which should trend toward zero once trimming logic is in place.
  • avg_tokens_per_request over time, per queue — catches a macro or canned-response template that's silently bloating prompts.

2RAG / knowledge-base Q&A app

Retrieval quality drives prompt size directly — too many or too-large retrieved chunks and you're paying to feed context the model barely uses, or blowing past its window outright.

Integration steps

  1. After retrieval, assemble the candidate prompt (query + top-k chunks) and run /analyze before generation, not after.
  2. Use the response's context_utilization to right-size k — if it consistently sits well under the window, fewer chunks (or a smaller-window model) likely does the same job for less.
  3. On WARNING/EXCEEDED, drop chunks or route to a bigger-window model before ever calling the LLM.
  4. Run /project with a few representative query archetypes and expected monthly volume to forecast the pipeline's total spend before shipping.

What to measure

  • The live distribution of context_utilization — how close to the ceiling real requests actually run.
  • WARNING + EXCEEDED share of traffic, which should fall as chunk-count tuning improves.
  • Projected vs. actual monthly cost — /project's forecast against a real /report built from production traffic.

3AI coding assistant / IDE plugin

Sending relevant file/code context alongside a prompt is what makes a coding assistant useful — and also the single biggest lever on both cost and whether the request fits the model's window at all.

Integration steps

  1. Before sending a completion/chat request, run /analyze with the assembled prompt (open files + selection + conversation) against the target model.
  2. On EXCEEDED, fall back to summarized distant context or a bigger-window model instead of letting the provider reject the call.
  3. If the product supports BYOK Claude/Gemini keys, use /analyze/exact so the token count shown to a developer is the provider's own number, not an estimate.
  4. Label every real request by feature (autocomplete, chat, refactor) and consolidate with /report weekly to see which feature actually drives spend.

What to measure

  • known_model + confidence on each response — flags requests silently using the heuristic fallback instead of a real provider count.
  • Cost per feature via by_label — autocomplete vs. chat vs. refactor.
  • EXCEEDED count trend after adding a context-trimming step — should drop toward zero.

4Multi-tenant content-generation SaaS

A platform generating blog posts, ad copy, or product listings on behalf of many customers needs per-customer cost visibility — both to price plans sanely and to catch one runaway customer before it eats the month's margin.

Integration steps

  1. Create one Workspace per customer (or per internal team), and route every generation call through that project's /projects/{id}/tools/analyze/runs (or tools/exact/runs for BYOK) endpoint so each result is saved against that customer automatically.
  2. Enforce per-plan limits in your own app logic using each call's estimated_cost/status before committing to the send.
  3. Pull GET /projects/{id}/report/consolidated per customer for real usage-to-date, and GET /workspaces/{id}/comparison to rank customers by spend across the whole workspace.
  4. Export either as a downloadable PDF (.../report/consolidated.pdf, .../comparison.pdf) for finance or a customer-facing usage statement.

What to measure

  • Cost per customer per billing period, straight from each project's consolidated report — no separate cost-tracking system needed.
  • A ranked, workspace-wide comparison to spot the top spenders before the invoice run.
  • Plan-limit breach rate — how often a customer's calls land as WARNING/EXCEEDED against their allotted budget.

5Batch / ETL document summarization pipeline

A nightly job summarizing logs, transcripts, or documents at volume fails expensively when it dies partway through a long run — and by the time anyone notices, that night's AI spend is already gone.

Integration steps

  1. Before each item enters the batch, run a quick /analyze pass (or use the core airi library in-process, via the compiled download on the Developers page, if the pipeline is Python and shouldn't take on a network dependency) to catch oversized documents up front.
  2. Route oversized items into a chunk-summarize-then-combine pattern instead of one call that would exceed the window.
  3. Collect every item's result with a phase tag ("normal" vs. a backlog-catchup run) and a timestamp, then POST the full batch to /report once the job finishes.
  4. Watch duration_seconds/requests_per_second alongside total_cost — a run that's both slower and pricier than last time usually means something upstream changed (bigger documents, a model swap).

What to measure

  • EXCEEDED items caught pre-flight vs. what would have failed mid-batch — the whole point of checking ahead of the call, not after.
  • total_cost and total_tokens night-over-night, to catch drift before it becomes a surprise on the monthly bill.
  • requests_per_second as a pipeline health signal, not just a cost one.

6CI/CD cost-and-context regression gate

Prompt templates and RAG context drift as people ship features — a gate that measures the change in cost/context footprint before merge catches that drift in review, not after a bill spikes in production.

Integration steps

  1. In CI, run your project's real prompt-construction code against a fixed set of representative inputs and POST each result to /analyze (or the compiled core library in-process — no network dependency needed for the check itself).
  2. Fail the build (or just warn) if status flips from SAFE to WARNING/EXCEEDED for any fixed input, or if estimated_cost rises past a set threshold versus the last merged run.
  3. Consolidate the run's results into a /report and archive it (or /report/pdf) as a build artifact, so a reviewer can see exactly what changed.
  4. For a fleet-wide view before a broad rollout, run /project with the team's known call-sites and expected volumes to forecast the change's total cost impact.

What to measure

  • Per-fixed-input estimated_cost delta between builds — a real, comparable number reviewers can look at in a diff.
  • status flips (SAFE→WARNING/EXCEEDED) per PR — a leading indicator, not a lagging one.
  • Projected fleet-wide cost delta via /project, before a prompt or model change ships broadly.

One company, six systems: a global network infrastructure provider

Real projects rarely start from a blank slate — they layer AI onto whatever enterprise systems already run the business. Take a large B2B hardware manufacturer that sells networking and connectivity infrastructure to enterprises and telecom operators worldwide: it already runs a fairly standard stack of six systems, and every one of them is a candidate for an AI feature, for exactly the same reason as above — check the request before you send it, not after.

7ERP & supply chain — an AI copilot over SAP/PLM data

Plant managers and planners need answers like "what's our raw-material shortage risk for Q3 cable production?" — which means pulling live ERP/PLM tables (inventory, bills of materials, supplier lead times) and handing them to a model as context. Those table dumps are exactly the kind of request that quietly balloons in size as a plant adds SKUs or suppliers.

Integration steps

  1. After the ERP query runs, assemble the data-plus-question prompt and check it with /analyze before generation — a bad join or an unfiltered date range can produce a huge table dump without anyone intending it to.
  2. On WARNING/EXCEEDED, pre-aggregate the ERP result (fewer rows, summarized columns) instead of sending the raw export.
  3. Create one Workspace per manufacturing plant so each plant's copilot usage is tracked separately from the start.
  4. Run /project across all plants with expected query volume per plant to forecast the rollout's total cost before turning it on globally.

What to measure

  • context_utilization per plant — a plant that's consistently near the ceiling has a data-shaping problem, not a model-size problem.
  • Cost per plant via each workspace's consolidated report, and a ranked /workspaces/{id}/comparison across all plants.
  • EXCEEDED rate trend as plants add SKUs/suppliers over the year.

8CRM & sales — AI account summaries at global scale

Reps across every region get an AI-drafted account summary or next-best-action note pulled from CRM opportunity and interaction history before a call. A distributor account that's been active for a decade has a very different context size than one signed last month — and this is customer-facing content, where a silently-wrong token estimate is worse than an API call that simply costs more.

Integration steps

  1. Before drafting, run /analyze (or /analyze/exact for real Claude/Gemini counts, since accuracy matters more than usual here) on the assembled account-history prompt.
  2. On EXCEEDED, summarize older interaction history instead of truncating it silently — a rep should never get a summary built from an arbitrarily cut-off history.
  3. Label every real call by sales region and consolidate with /report weekly.
  4. Use by_label in the report to compare regions with very different account-book sizes (a 20-year enterprise territory vs. a new reseller market).

What to measure

  • Cost per rep and per region, via by_label — flags a region whose account histories have grown unusually large.
  • confidence on Exact-mode responses — a dip signals the provider call is failing more often and falling back to the heuristic for that region.
  • EXCEEDED count trend after the history-summarization step ships.

9B2B partner portal — an AI product & ordering assistant

Distributors ordering hardware through a self-service portal need help finding the right SKU or spec out of a catalog with thousands of parts — a retrieval-style assistant over the product catalog, not unlike the RAG scenario above, but with a partner tier and order history layered on top.

Integration steps

  1. After catalog retrieval, run /analyze on the assembled query + top-k spec-sheet chunks before generation, same as any RAG pipeline.
  2. Use context_utilization to right-size how many spec sheets get pulled in per query — catalog chunks are often far bigger than they need to be for a simple "which connector fits X" question.
  3. Create one Workspace per major distributor tier (or per key account) and route each partner's assistant calls through that project's tool-run endpoints, exactly as in the multi-tenant SaaS scenario above.
  4. Give each key account's team a consolidated PDF report of their own assistant usage via .../report/consolidated.pdf — a natural fit for a quarterly partner-account review.

What to measure

  • Cost per partner tier, straight from each workspace's consolidated report.
  • The live distribution of context_utilization — how much catalog data each query actually needed versus what was sent.
  • WARNING/EXCEEDED share for partners with unusually broad catalog access (a global distributor carrying the full SKU range vs. a regional reseller with a narrow one).

10Infrastructure & data-center management — AI ops summaries

A DCIM (data-center infrastructure management) platform tracks switch maps, rack capacity, and power/cooling telemetry across every site. An AI layer that turns a night's raw telemetry into a plain-language ops report for the morning stand-up is exactly the batch-pipeline pattern above, applied per site, at real infrastructure scale — hundreds of sites, each with its own telemetry volume.

Integration steps

  1. Before summarizing a site's telemetry, run /analyze per site to catch the handful of unusually large sites (more racks, denser instrumentation) before they blow the window.
  2. Route oversized sites into a chunk-summarize-then-combine pattern rather than one call per site — the same fix as the batch/ETL scenario above, just per-site instead of per-document.
  3. Tag each site's result with a label (site id/region) and a phase ("nightly" vs. an on-demand incident run), then consolidate the whole night's sweep with one /report call.
  4. Watch requests_per_second/duration_seconds across the fleet sweep as an early signal that a site's telemetry volume has grown — before it shows up as a support ticket.

What to measure

  • EXCEEDED sites caught pre-flight, by by_label (site/region) — tells you exactly which sites need the chunking path.
  • total_cost per fleet sweep, night-over-night, to catch the sweep quietly getting more expensive as the network grows.
  • requests_per_second as a fleet health signal — a sudden drop often means a subset of sites is timing out, not just running slow.

11BI & analytics — an AI narrative layer over the dashboard

Executive dashboards show factory output, revenue, and supply-chain risk — but a dashboard alone doesn't answer "so what changed this week and why." An AI layer that turns a BI query result into a short written narrative, delivered alongside the dashboard, is a natural extension once the numbers already exist.

Integration steps

  1. Before generating the narrative, run /analyze on the assembled dashboard-snapshot-plus-question prompt — a dashboard with many metrics/breakdowns can produce a surprisingly large context.
  2. Use /analyze/exact for the real provider token count on executive-facing output, where predictable cost matters more than for an internal tool.
  3. Run /project before increasing refresh frequency (weekly → daily) or rolling the narrative out to more dashboards, to forecast the cost step-change ahead of time.
  4. Consolidate a month of narrative runs with /report, labeled by dashboard/team, for a simple cost-per-dashboard view finance can read directly.

What to measure

  • Cost per report-run via by_label (per dashboard/team), and how it moves as a dashboard grows more metrics.
  • Projected vs. actual cost when refresh frequency changes — /project's forecast against the following month's real /report.
  • EXCEEDED rate as a leading indicator that a dashboard has outgrown a single-call narrative and needs its own summarize-then-combine step.

12Enterprise collaboration — a company-wide AI assistant

An AI assistant embedded in the collaboration suite answers employee questions by pulling context from meeting transcripts, shared documents, and chat history — used by a global workforce, at every scale from a quick one-line question to "summarize this 90-minute transcript."

Integration steps

  1. Run /analyze per query in real time — latency-sensitive, so this is a pre-flight check on the critical path, not a batch job.
  2. On EXCEEDED (a full transcript or long document dump), switch to a chunk-summarize-then-combine path instead of failing the request outright.
  3. Create one Workspace per business unit/department so cost is visible per team from day one, not discovered later in one combined bill.
  4. Treat prompt-template changes to the assistant like the CI/CD scenario above — this is the one place a small template change reaches every employee in the company at once, so gate it the same way.

What to measure

  • Cost per department/BU via /workspaces/{id}/comparison across the whole company.
  • EXCEEDED rate for long-document/transcript requests specifically, versus quick questions — two very different usage patterns worth tracking separately.
  • Company-wide average cost per query over time — the number most likely to actually end up in a budget conversation.

Every metric above comes straight off a response AIRI already returns — nothing here needs a separate analytics pipeline. Mix and match across scenarios freely; most real projects are a combination of two or three of these, not just one.
