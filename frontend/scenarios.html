Usage scenarios by project type

Six concrete project types, each with the exact AIRI calls to wire in and what becomes measurable once you have — not hypothetical benchmarks, just the metrics each endpoint's own response already hands you. See What is AIRI? for what each piece does, and the Developers page for the full API reference every step below links back to.

1Customer support / AI helpdesk chatbot

Every inbound message goes to an LLM before a human sees it — one bad week (a viral thread, an outage spawning duplicate tickets) can spike the bill overnight if nothing checks size or cost per call first.

Integration steps

  1. Before generating a reply, send the message + conversation history to /analyze (or /analyze/exact once signed in, for real Claude/Gemini counts) with the model you'll actually use.
  2. If status comes back EXCEEDED, summarize or drop older turns rather than sending an oversized request and letting the provider reject it.
  3. Tag each real call's result with a label per queue (e.g. "billing", "technical") as it happens through the day.
  4. At shift end, POST the collected records to /report (or /report/pdf for a shareable summary) for a per-queue breakdown.

What to measure

  • Cost per conversation — total_cost / total_requests from /report, tracked per queue via by_label.
  • Overflow rate — status_counts.EXCEEDED / total_requests, which should trend toward zero once trimming logic is in place.
  • avg_tokens_per_request over time, per queue — catches a macro or canned-response template that's silently bloating prompts.

2RAG / knowledge-base Q&A app

Retrieval quality drives prompt size directly — too many or too-large retrieved chunks and you're paying to feed context the model barely uses, or blowing past its window outright.

Integration steps

  1. After retrieval, assemble the candidate prompt (query + top-k chunks) and run /analyze before generation, not after.
  2. Use the response's context_utilization to right-size k — if it consistently sits well under the window, fewer chunks (or a smaller-window model) likely does the same job for less.
  3. On WARNING/EXCEEDED, drop chunks or route to a bigger-window model before ever calling the LLM.
  4. Run /project with a few representative query archetypes and expected monthly volume to forecast the pipeline's total spend before shipping.

What to measure

  • The live distribution of context_utilization — how close to the ceiling real requests actually run.
  • WARNING + EXCEEDED share of traffic, which should fall as chunk-count tuning improves.
  • Projected vs. actual monthly cost — /project's forecast against a real /report built from production traffic.

3AI coding assistant / IDE plugin

Sending relevant file/code context alongside a prompt is what makes a coding assistant useful — and also the single biggest lever on both cost and whether the request fits the model's window at all.

Integration steps

  1. Before sending a completion/chat request, run /analyze with the assembled prompt (open files + selection + conversation) against the target model.
  2. On EXCEEDED, fall back to summarized distant context or a bigger-window model instead of letting the provider reject the call.
  3. If the product supports BYOK Claude/Gemini keys, use /analyze/exact so the token count shown to a developer is the provider's own number, not an estimate.
  4. Label every real request by feature (autocomplete, chat, refactor) and consolidate with /report weekly to see which feature actually drives spend.

What to measure

  • known_model + confidence on each response — flags requests silently using the heuristic fallback instead of a real provider count.
  • Cost per feature via by_label — autocomplete vs. chat vs. refactor.
  • EXCEEDED count trend after adding a context-trimming step — should drop toward zero.

4Multi-tenant content-generation SaaS

A platform generating blog posts, ad copy, or product listings on behalf of many customers needs per-customer cost visibility — both to price plans sanely and to catch one runaway customer before it eats the month's margin.

Integration steps

  1. Create one Workspace per customer (or per internal team), and route every generation call through that project's /projects/{id}/tools/analyze/runs (or tools/exact/runs for BYOK) endpoint so each result is saved against that customer automatically.
  2. Enforce per-plan limits in your own app logic using each call's estimated_cost/status before committing to the send.
  3. Pull GET /projects/{id}/report/consolidated per customer for real usage-to-date, and GET /workspaces/{id}/comparison to rank customers by spend across the whole workspace.
  4. Export either as a downloadable PDF (.../report/consolidated.pdf, .../comparison.pdf) for finance or a customer-facing usage statement.

What to measure

  • Cost per customer per billing period, straight from each project's consolidated report — no separate cost-tracking system needed.
  • A ranked, workspace-wide comparison to spot the top spenders before the invoice run.
  • Plan-limit breach rate — how often a customer's calls land as WARNING/EXCEEDED against their allotted budget.

5Batch / ETL document summarization pipeline

A nightly job summarizing logs, transcripts, or documents at volume fails expensively when it dies partway through a long run — and by the time anyone notices, that night's AI spend is already gone.

Integration steps

  1. Before each item enters the batch, run a quick /analyze pass (or use the core airi library in-process, via the compiled download on the Developers page, if the pipeline is Python and shouldn't take on a network dependency) to catch oversized documents up front.
  2. Route oversized items into a chunk-summarize-then-combine pattern instead of one call that would exceed the window.
  3. Collect every item's result with a phase tag ("normal" vs. a backlog-catchup run) and a timestamp, then POST the full batch to /report once the job finishes.
  4. Watch duration_seconds/requests_per_second alongside total_cost — a run that's both slower and pricier than last time usually means something upstream changed (bigger documents, a model swap).

What to measure

  • EXCEEDED items caught pre-flight vs. what would have failed mid-batch — the whole point of checking ahead of the call, not after.
  • total_cost and total_tokens night-over-night, to catch drift before it becomes a surprise on the monthly bill.
  • requests_per_second as a pipeline health signal, not just a cost one.

6CI/CD cost-and-context regression gate

Prompt templates and RAG context drift as people ship features — a gate that measures the change in cost/context footprint before merge catches that drift in review, not after a bill spikes in production.

Integration steps

  1. In CI, run your project's real prompt-construction code against a fixed set of representative inputs and POST each result to /analyze (or the compiled core library in-process — no network dependency needed for the check itself).
  2. Fail the build (or just warn) if status flips from SAFE to WARNING/EXCEEDED for any fixed input, or if estimated_cost rises past a set threshold versus the last merged run.
  3. Consolidate the run's results into a /report and archive it (or /report/pdf) as a build artifact, so a reviewer can see exactly what changed.
  4. For a fleet-wide view before a broad rollout, run /project with the team's known call-sites and expected volumes to forecast the change's total cost impact.

What to measure

  • Per-fixed-input estimated_cost delta between builds — a real, comparable number reviewers can look at in a diff.
  • status flips (SAFE→WARNING/EXCEEDED) per PR — a leading indicator, not a lagging one.
  • Projected fleet-wide cost delta via /project, before a prompt or model change ships broadly.

Every metric above comes straight off a response AIRI already returns — nothing here needs a separate analytics pipeline. Mix and match across scenarios freely; most real projects are a combination of two or three of these, not just one.
