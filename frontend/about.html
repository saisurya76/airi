What is AIRI?

AIRI (AI Request Intelligence) is a pre-flight check for AI requests: before you send a prompt to a model, it estimates how many tokens it'll use, how much context window that eats into, and roughly what it'll cost — so your app can decide to send, modify, or reject the request, instead of finding out after the fact. It's not a token counter you paste text into; it's a small library + API meant to sit in front of your own AI calls.

1Check a single request

The main box on the try-it page. Paste a prompt (or the request you're planning to send), pick a model, optionally say how many output tokens you expect, and hit Analyze request.

  1. You get back input/output/total token counts, an estimated cost in USD, and how much of that model's context window the request would use.
  2. A status badge tells you where you stand: SAFE WARNING EXCEEDED — exact thresholds are in the API reference on the Developers page.
  3. OpenAI models are counted exactly via tiktoken; everything else uses a fast, honest character-based heuristic by default — see "Exact mode" below for real Claude/Gemini counts.
  4. If your app uses prompt caching (Anthropic prompt caching, OpenAI's automatic caching, Gemini context caching), click "+ Using prompt caching?" under Model/Expected output tokens and say how many of this request's tokens are a fresh cache write vs. an existing cache read. The cost breaks out fresh/write/read/output separately, plus a "cache savings" number — positive means caching saved money on this request, negative is normal on a write-only request (the saving shows up on later reads of that entry, not the request that created it). AIRI doesn't detect caching for you — it only prices it once you say how many tokens were involved, and a model with no published cache price is billed at the plain input rate, never guessed.

2Exact mode — real Claude/Gemini token counts

Click Exact ▸ at the top of the single-request box to switch from estimating Claude/Gemini requests to calling that provider's own token-counting API directly (OpenAI models are already exact either way).

  1. Sign in with just your email — you'll get a one-time 6-digit code, no password to set or remember. This exists purely to keep shared capacity from being hammered by anonymous traffic, not to paywall anything.
  2. Once you're signed in, one of two things happens, depending on how this deployment is configured:
    • Testing mode: you're done — AIRI uses its own shared Anthropic/Gemini keys for you.
    • BYOK (bring your own key): a small panel asks for your own Anthropic and/or Google (Gemini) API key. It's stored only in your browser and sent along with each Exact request — AIRI never stores it server-side. Use "Manage keys" (next to your email, once signed in) to add, change, or clear it later.
  3. Exact requests return the same fields as Standard, plus method: "provider-api" and higher confidence — if the provider call ever fails, AIRI quietly falls back to the heuristic and says so honestly rather than mislabeling the number.
Which mode a deployment is in is a runtime setting controlled server-side by whoever operates it — not something end users choose.

3Project cost across your whole app

The Traffic projection section below the single-request box. A real app rarely sends just one kind of request — it has a handful of distinct call-sites (a chat reply, a summary, a classification, etc.), each hit some number of times.

  1. Add one row per distinct AI call-site: a name, a representative sample request, the model it uses, and how many times you expect to call it (from your own analytics or projections — AIRI doesn't guess volume).
  2. Click Run projection to get a per-row and grand-total token/cost breakdown, plus a per-model summary.
  3. Each row can also take cache-write/cache-read token counts, same as a single request — useful since a repeated archetype (the same call-site run many times) is exactly where caching a fixed system prompt or history prefix pays off most. When any row uses it, the result shows a "cached" tag per row plus a total cache savings line under the table.

4Consolidate a load test into a report

The Load-test token usage report section. To be clear about what "load test" means here: it's your own service under load (from k6, JMeter, Locust, your own scripts — any language, any tool), not AIRI itself. AIRI doesn't run the load or generate traffic; it just estimates each request as your test fires it, and consolidates everything into one report once the run is done.

Concretely, once /analyze is already wired into your service calls (see step 5 below): as your load test runs, keep every /analyze result your harness already gets back, tagged with a label (which call-site it was) and, optionally, a phase (e.g. "normal" vs "peak") and a timestamp. At the end of the run, POST the whole collected list once to /report:

import requests

records = []  # filled in as your load test runs — see below

def guarded_call(prompt, model, expected_output_tokens, label, phase="normal",
                  cache_write_tokens=0, cache_read_tokens=0):
    """Every AI call your service makes during the load test goes through here."""
    check = requests.post("http://localhost:8000/analyze", json={
        "prompt": prompt, "model": model, "expected_output_tokens": expected_output_tokens,
        "cache_write_tokens": cache_write_tokens, "cache_read_tokens": cache_read_tokens,
    }).json()
    records.append({**check, "label": label, "phase": phase})
    return check

# ... your load-test tool drives guarded_call() for every request in the run ...

# Once the run finishes, submit everything collected in one call:
report = requests.post("http://localhost:8000/report", json={
    "run_name": "Nightly load test", "records": records,
}).json()
print(f"{report['total_requests']} requests, ${report['total_cost']:.2f}, {report['status_counts']}")
  1. You get back totals, a SAFE/WARNING/EXCEEDED breakdown, per-label/per-model/per-phase rollups, and the worst-offending requests — plus a downloadable, presentation-ready PDF (/report/pdf, same body).
  2. Nothing is stored server-side: you submit the records from a run you already have, AIRI just does the arithmetic and renders the report. Run it again tomorrow with a fresh set of records and you get a fresh report — there's no history to manage or clean up.
  3. Cache-write/cache-read token counts (see step 1) work here too — each service row on the try-it page has the same toggle, and since a report's records are just whatever /analyze results you hand it, total_cost already reflects caching once the records that produced it do.
  4. The section on the try-it page simulates this whole flow with made-up services so you can see the report it produces without wiring anything up first. The pattern above is language-agnostic: collect each /analyze result in a JS array from k6, append it to a shared list from a JMeter post-processor, or just build up the same JSON from a plain shell script piping curl output — anything that can call /analyze and hold onto the results can build this records list.

7Beyond API traffic: license & SDLC tool requests

An "AI request" inside a company isn't only API calls a developer wires up — it's also the per-seat license a department asks for (Microsoft 365 Copilot, Cowork, ChatGPT Enterprise...) and the SDLC tool a dev team asks for (GitHub Copilot, Microsoft Foundry, Cursor...). AIRI covers both the same way it covers API traffic: pick a real vendor from a list of major tools in that category, AIRI tries to fetch its current public price live off the vendor's own pricing page (not a stored number — some vendors don't publish a plain price at all, in which case you enter your own), say how many seats you need, and get a monthly/annual total.

  1. Kept apart from the API demo since the request shape is different: License request wizard.
  2. Same idea for dev tools: SDLC tool request wizard.
  3. Run any of the demos above and each one's result rolls into a combined monthly total shown at the end — a management-level view across every kind of AI spend, not just API bills.
